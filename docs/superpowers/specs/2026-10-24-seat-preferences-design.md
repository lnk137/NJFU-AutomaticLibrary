# Personal seat preferences

## Agreed behavior
Each account saves its own favorite seats, custom tags and named groups of 1–5 ordered seats. No shared groups or predefined tags. Root may manage the selected account through existing permissions. Choosing a group fills only the current seat-selection draft; existing apply/save controls remain authoritative. Editing or deleting a group/favorite never edits a saved plan, date exception, manual preview or reservation.

## Implementation
- Add `seat_preferences` and `seat_preferences_revision` to the account document/view, with empty defaults and no migration. Metadata writes CAS only their own revision; do not change account revision, credential revision, plan, date exceptions or runs, and do not acquire booking locks or call school APIs.
- `GET/PUT /api/local/accounts/<id>/seat-preferences` use existing authentication/ownership/Origin/CSRF boundaries. PUT replaces the complete metadata snapshot with `expected_revision`. A missing or stale revision cannot overwrite newer metadata.
- Shape: favorites `[{seat_id,tags:[string]}]`, groups `[{id,name,seat_ids:[string]}]`. Up to 100 favorites, 20 groups, 5 tags per favorite (20 characters each), group names up to 40 characters, and 1–5 distinct catalog seats per group. Trim/deduplicate tags. Reject malformed, duplicate or newly introduced unknown seats and IDs without changing data. If a later catalog omits a seat, an existing reference may remain in its original favorite/group so that other invalid entries can be repaired or removed independently. Existing groups can open for repair; applying any unavailable group is refused rather than silently dropping seats.
- Reuse a compact SeatLibrary component in the normal/today seat drawer and one-day exception editor. Provide All/Favorites/Groups tabs, a favorite toggle per seat, tag editing, and group creation from the current ordered selection, rename/update/delete and apply. Keep existing parent draft ordering, application and leave protection. Library metadata uses its own request guards and never overwrites selection when a response arrives.
- Account/session changes discard private library responses. Each metadata editor retains its original version and baseline through draft restoration and automatic reads. Conflicts preserve input; explicit reload rebases untouched fields on remote data, preserves edited fields, and requires another save after inspection. Deleted targets cannot be silently recreated. Separate metadata editors protect unsaved text before closing/navigation. Offline account mirrors already carry AccountView; allow selecting cached favorites/groups into existing drafts, while metadata editing requires the campus backend online.

## Verification and boundaries
Use the existing worktree/dependencies and isolated Mongo/school fixtures. Cover independent revisions and locks, stale writes, account privacy, metadata normalization, tags, group ordering, draft snapshots, unchanged plans/history/credentials, stale UI responses, offline read-only use and dirty-editor protection. Verify first-feature regressions, complete backend/frontend suites, H5 build and isolated browser. No production data/service/school access, commits, push, dependency installation or activation. Preserve the first feature and its evidence.
